# Implementation Plan: JDBC User Authentication

**Branch**: `002-jdbc-user-authentication` | **Date**: 2026-09-26 | **Spec**: [spec.md](spec.md)

**Input**: Feature specification from `/specs/002-jdbc-user-authentication/spec.md`

**Note**: Plan produced by `/speckit.plan`; detailed task breakdown is produced later by
`/speckit.tasks` into `tasks.md`.

## Summary

Deliver sign-in / sign-out for the admin console using Spring Security JDBC authentication
(the mechanism mandated in the spec assumptions) against the application's own embedded H2
database. JDBC authentication verifies identity and account status only; the permission
enforcement already designed in feature 001 (per-request `AuthorizationManager` resolving the
effective permission set from `user_roles` -> `roles` -> `permissions`) remains the sole
authorization gate, so grants/revokes and deactivation take effect immediately without
re-login. The feature adds a hashed-credential column to the existing `users` entity, a
supporting `auth_event` table for the reviewable sign-in/failure/sign-out stream (FR-013),
an in-memory bounded failed-attempt throttle (FR-012), session-fixation-safe login with
redirect-back (FR-007/FR-008), and a CoreUI-based sign-in screen with a single generic
invalid-credentials message (FR-003). Full design decisions in [research.md](research.md);
interface contracts in [contracts/](contracts/README.md); data model in
[data-model.md](data-model.md).

## Technical Context

**Language/Version**: Java 21 (constitution Principle III: Java 21 LTS or newer; `pom.xml`
sets 21)

**Primary Dependencies**: Spring Boot 4.1.x (`spring-boot-starter-parent` 4.1.1) with Spring
Security 7.x; `spring-boot-starter-security` (present in `pom.xml`),
`spring-boot-starter-data-jdbc` (present — provides the `DataSource`/`JdbcTemplate` context
`JdbcUserDetailsManager` needs); `spring-boot-starter-web`, `spring-boot-starter-thymeleaf`,
`spring-boot-starter-validation`, H2, Hibernate/JPA from the feature-001 stack;
`spring-boot-starter-test` and `spring-security-test` (testing)

**Storage**: Embedded H2, schema still generated by Hibernate (`ddl-auto`) per constitution
Principle III. JDBC authentication reads the identity data over raw JDBC against the same
H2 `DataSource`; it does not create any schema of its own. `users` gains a
`password_hash` column; a supporting `auth_event` table is added (see Complexity Tracking).

**Testing**: JUnit 5 + MockMvc with spring-security-test: login success/failure/refusal
flows, redirect preservation, new-session-id verification, throttle windows, auth-event
recording, and the constitution-mandated dual-sided authorization checks (permitted → 200,
denied → 302/403). Feature-001 suites continue to cover RBAC screen boundaries.

**Target Platform**: Server-rendered admin web application; standard desktop web browsers.

**Project Type**: Web application (admin console) — single Spring Boot Maven project.

**Performance Goals**: SC-001 — reach home in <10s after credential submission (UI-level;
standard <2s responsiveness). SC-007 — automated guessing cannot exceed a small, bounded
number of attempts per account per minute (see throttle design, D-3).

**Constraints**: Fail-closed security (every protected route requires authentication AND the
required permission); permission set resolved per request before controllers (constitution
Principle II); Java Bean Validation on mutations; UUID (v4) PKs; UTC timestamps;
`anyRequest().authenticated()` with a whitelist of `/login`, `/css/**`, `/js/**`,
`/assets/**`, `/error`; generic errors, no credential material ever persisted or logged;
throttle must not reveal account existence.

**Scale/Scope**: Single organization, single local identity store; tens to low hundreds of
accounts; ~6 protected screens already defined in feature 001.

## Complexity Tracking

> Fill ONLY if Constitution Check has violations that must be justified.

| Violation | Why Needed | Simpler Alternative Rejected Because |
|-----------|------------|-------------------------------------|
| Supporting `auth_event` table beyond the five core RBAC tables (and beyond 001's `audit_event`) | FR-013 requires every sign-in/failure/sign-out reviewable with account, time, outcome — including failures for unknown usernames, which have no FK target | Reusing `audit_event`: pollutes the admin-mutation audit and cannot cleanly represent unknown-username failures (no target id); in-memory/log-only: not durable or reviewable |
| Per-request permission re-resolution via `AuthorizationManager` (middleware) for every request | Constitution Principle II mandates the active permission set be resolved per request before controller dispatch, and FR-004/SC-006 require deactivation and revokes to take effect immediately | Relying on privileges baked into the JDBC `UserDetails` at login: revokes/deactivations would persist until re-login, violating Principle II and SC-006 |
| In-memory failed-attempt throttle (D-3) | FR-012/SC-007 bound guessing attempts in a single-process embedded app, with no external service | DB-persisted lockout: higher write volume and risks leaking account existence via lock state; keyed/IP-only counters fail OWASP guidance and FR-012's per-account semantics |

## Decisions (research.md)

- D-1 JDBC identity leg: `JdbcUserDetailsManager` with custom queries over existing `users`
- D-2 Password: `DelegatingPasswordEncoder` (`{bcrypt}` default) + lazy upgrade; dummy hash for unverifiable credentials
- D-3 Throttle: in-memory `LoginAttemptRegistry`, 5 fails / 15 min, block-before-authenticate, uniform for known/unknown usernames
- D-4 Authorization: JDBC proves identity only; `AuthorizationManager` is the sole gate, re-resolves per request
- D-5 Sessions: default `changeSessionId` fixation protection, `HttpSessionRequestCache` redirect-back; concurrent sessions allowed; authenticated `/login` → home
- D-6 Events: success/failure/logout handlers persist `auth_event`; never credentials
- D-7 Usernames: trim on input; case-insensitive via `LOWER()` in SQL; cross-feature note for 001 creation normalization
